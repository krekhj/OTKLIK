# HHBot — автоприём откликов на hh.ru

Бот логинится на hh.ru, включает фильтры поиска и откликается на N вакансий,
прикрепляя сопроводительное письмо. Вакансии с анкетами работодателя пропускает.

> ⚠️ Массовые автоматические отклики — это то, за что hh.ru может ограничить
> аккаунт. Используй осторожно: сначала `count = 1`, проверь руками, потом
> увеличивай.

## Быстрый старт

```bash
# сервер (API на :3000, без фреймворков — чистый node:http)
cd server && npm install && cp .env.example .env
npm run dev

# фронт (Vite проксирует /api на :3000)
cd client && npm install && npm run dev
```

Логин, пароль, ключевые слова, число откликов и письмо вводятся на странице —
в коде ничего хранить не нужно. Пароль живёт только в памяти на время прогона
и в браузере не сохраняется.

Вход — двумя способами, переключатель возле «01 ACCOUNT»:

- **PASSWORD** — email и пароль;
- **EMAIL CODE** — email, затем hh шлёт код на почту; бот присылает запрос на
  страницу (панель EMAIL CODE, бейдж CODE в шапке), человек вводит код.
  Неверный код — спросит снова, до `LIMITS.codeAttempts` (5) раз. Код может быть
  одним полем или клетками по цифре — `typeCode()` справляется с обоими.
  Селектор поля — `login.codeInput`, текст ошибки — `BAD_CODE_TEXT`.

Сессия hh.ru сохраняется в `sessions/<hash логина>.session`, зашифрованной
секретом: в режиме пароля — паролем пользователя, в режиме кода — случайным
«ключом устройства», который браузер генерирует и хранит в localStorage
(`entities/run/lib/deviceKey.ts`). Повторный запуск с того же браузера пройдёт
без кода, с другого — потребует новый код. Шифр: scrypt → AES-256-GCM, логин — AAD. Бот подхватывает её,
только с тем же логином и тем же паролем (или ключом устройства); иначе — обычный вход,
где пароль или код проверяет hh. Сессия пересохраняется в конце каждого прогона (и при
STOP), а если hh её не принял — файл удаляется. Файл, который не удалось
расшифровать, не удаляется: иначе чужой email с неверным паролем стирал бы
чужую сессию. Код — `src/hh-bot/bot.session.ts`.

Если при входе hh показал капчу, бот не распознаёт её сам: делает скриншот
картинки и отправляет на страницу (панель CAPTCHA над статусом, в шапке —
бейдж CAPTCHA). Человек вводит текст или просит другую картинку, бот вписывает
ответ. Пока капча ждёт, таймаут входа не тикает.

С `HEADLESS=false` окно открывается только для входа. После входа бот сохраняет
сессию и перезапускает Chromium без окна, а картинки, видео и шрифты блокирует:
под Xvfb на слабом VPS отрисовка замедляла каждый отклик в разы. Если есть
сохранённая сессия, окно не открывается вовсе. В логе у каждой вакансии указано,
сколько секунд она заняла.

Неверный логин или пароль: бот читает ошибку hh под формой («Неверный email или
пароль» — селектор `login.error`, текст `BAD_CREDENTIALS_TEXT`) и завершает
прогон с `bad_credentials`, фронт подсвечивает оба поля. Если hh вместо ошибки
просто показывает капчу снова, после `LIMITS.loginCaptchas` (3) капч подряд
прогон тоже завершается как `bad_credentials`. Код капчи — `src/hh-bot/bot.captcha.ts`, ответ —
`POST /api/run/captcha`. Без фронта: `HH_LOGIN=… HH_PASSWORD=… npm run session`
и пройти капчу руками в открытом окне.

Продакшен без Docker: `cd client && npm run build`, затем в `server/`
`npm run build && npm start` (запускает `node dist/main.js`) — сервер сам раздаёт
`client/dist`. С Docker — см. корневой [README](../README.md).

Переменные окружения:

| Переменная | По умолчанию | Что |
|---|---|---|
| `PORT` / `HOST` | `3000` / `127.0.0.1` | адрес API; не-localhost требует `AUTH_*` |
| `AUTH_USER` / `AUTH_PASSWORD` | — | Basic-авторизация на всё, кроме `/healthz` |
| `MAX_RUNS` | `2` | сколько прогонов (каждый — свой Chromium) может идти одновременно |
| `HEADLESS` | `false` | `false` — окно только на время входа (иначе hh не шлёт капчу), отклики всегда без окна; `true` — без окна всегда |
| `SESSIONS_DIR` / `DEBUG_DIR` | `sessions/` / `debug/` | сессии и дампы страниц |
| `CLIENT_DIR` | `../client/dist` | собранный фронт |

## Несколько пользователей

Basic-пароль один на всех, поэтому людей сервер различает по cookie
`otklik_client`: случайный id, который выдаётся при первом запросе
(`HttpOnly`, `SameSite=Strict`, `Secure` за HTTPS-прокси —
`shared/http/http.client.ts`). Каждый id — свой `RunStore`
(`shared/run/run.registry.ts`): статус, лог, капча, код и STOP видны и доступны
только этому браузеру. Ограничения при запуске:

- не больше `MAX_RUNS` одновременных прогонов → иначе `503 server is busy`;
- один hh-аккаунт — один прогон → иначе `409 already running in another browser`.

Завершённые прогоны без открытых вкладок забываются через сутки. Прогон
привязан к браузеру: открыть его с другого устройства нельзя (и так задумано).

## API

| Метод | Путь | Что делает |
|---|---|---|
| `GET` | `/healthz` | `{ok:true}` без авторизации — для healthcheck |
| `GET` | `/api/run` | текущее состояние прогона |
| `GET` | `/api/run/events` | SSE-поток состояния (живой прогресс) |
| `POST` | `/api/run/start` | `{login, authMode: "password"\|"code", password, deviceKey, keywords[], count, coverLetter, filters}` → 202; 422 с ошибками полей; 409 если уже идёт |
| `POST` | `/api/run/stop` | остановить (закрывает браузер) |
| `POST` | `/api/run/reset` | сбросить завершённый прогон в `idle` |
| `POST` | `/api/run/code` | `{code}` — код из письма; 409 если код не ждут |
| `POST` | `/api/run/captcha` | `{action:"solve", text}` или `{action:"refresh"}`; 409 если капча не ждёт |

## Как работает бот

### 1. Вход

`login()` открывает страницу входа, заполняет email и пароль, ждёт ухода со
страницы `/account/login`.

### 2. Поиск

`openSearch()` открывает выдачу сразу по URL с фильтрами из формы (левая
колонка «FILTERS» на странице):

| Фильтр | Параметр URL | Значения |
|---|---|---|
| регион | `area` | 113 Россия, 1 Москва, 2 СПб, 3 Екатеринбург, 4 Новосибирск, 88 Казань, 66 Н. Новгород |
| опыт | `experience` | `noExperience`, `between1And3`, `between3And6`, `moreThan6` (по умолчанию первые два) |
| формат работы | `work_format` | `REMOTE`, `HYBRID`, `ON_SITE`, `FIELD_WORK` |
| доход от | `salary` + `currency_code=RUR` | число |
| только с доходом | `only_with_salary=true` | |
| искать только в | `search_field` | `name`, `company_name`, `description` |
| слова-исключения | `excluded_text` | через запятую |
| другие | `label` | `not_from_agency`, `low_performance` (<10 откликов), `accredited_it` |

Все параметры сверены с живым hh (меняют число найденных вакансий), id
регионов — по `api.hh.ru/areas`. Белый список значений — `FILTER_OPTIONS` в
`bot.constants.ts`, на фронте — `features/configure-run/model/filters.ts`.
Тип занятости не добавлен: hh сменил его параметры.

Пример: `/search/vacancy?text=React OR Frontend&area=1&experience=between1And3&work_format=REMOTE`.
Дровер «Фильтры» не используется: у залогиненного пользователя он рисуется
иначе, и чекбоксы опыта в нём не находились (`locator.check: Timeout`).

### 3. Отклики

`respondToVacancies()` идёт по карточкам выдачи и на каждую вызывает
`respondToOne()`:

1. Клик «Откликнуться».
2. Дальше три варианта:
   - **Ушли со страницы выдачи** → это анкета работодателя. Возвращаемся
     (`returnToSerp`), вакансию пропускаем.
   - **Появилась модалка** → закрываем (`closeAnyDialog`), пропускаем.
   - **Появился блок «Ваш отклик отправлен работодателю»** → отклик ушёл,
     переходим к письму.
3. `attachLetter()` находит карточку по `vacancyId`, жмёт «Приложить письмо»,
   заполняет `coverLetter`, жмёт «Отправить».

После каждого отклика выдача перерисовывается, поэтому карточка каждый раз
ищется заново, а `handled` (набор уже обработанных `vacancyId`) защищает от
повторных кликов по одной и той же вакансии.

## Подводные камни hh.ru

Всё это выяснено на живом сайте и объясняет, почему код местами выглядит
неочевидно.

### 1. Радио «Почта» не кликается напрямую

Нативный `<input type="radio">` скрыт под стилизованным `<span>`. Playwright
кликает в геометрический центр input'а, делает hit-test и видит сверху `span` —
соседа, а не потомка. Отсюда бесконечные ретраи и `TimeoutError`
(«intercepts pointer events»). Решение — кликать по `<label>`-обёртке, браузер
сам активирует вложенный radio.

### 2. Отклик отправляется сразу, письмо — потом

Клик «Откликнуться» в выдаче отправляет отклик **без модалки**. Поле письма —
это отдельная форма, которая появляется уже после отклика (форма
`/applicant/vacancy_response/edit_ajax`, письмо прикрепляется к уже отправленному
отклику). Поэтому `coverLetter` заполняется вторым шагом, а не в модалке.

### 3. Анкета бывает в двух видах

- **Переходом** на `/applicant/vacancy_response?...startedWithQuestion`
  (URL содержит `startedWithQuestion`).
- **Модалкой** с `role="alertdialog"`.

Оба варианта надо пропускать.

### 4. `role="alertdialog"` ≠ `role="dialog"`

Окна вроде «Вакансия с прямым откликом» и «Вы откликаетесь на вакансию в другой
стране» используют `alertdialog`. Если ловить только `dialog`, такие окна не
заметятся.

### 5. Escape не закрывает alertdialog

Проверено: после Escape модалка остаётся на месте и перехватывает все
последующие клики. Поэтому `closeAnyDialog()` ищет кнопку отмены явно: по
`data-qa`, затем по тексту («Отмен…», «Закрыть», «Понятно»), и лишь потом —
Escape как последний шанс. Если закрыть не удалось — перезагружает выдачу.

### 6. Нельзя жать «главную» кнопку модалки

В окне «Вакансия с прямым откликом» основная кнопка
(`vacancy-response-link-advertising`) ведёт на **внешний сайт работодателя**
(например, yandex.ru). Закрывать окно надо строго через «Отменить».

### 7. У плашки «письмо отправлено» нет смысла в выдаче

После отправки письма в выдаче плашка `cover-letter-after-send` не появляется
(она есть только на странице вакансии). Поэтому подтверждением отправки служит
**исчезновение формы письма**, а не появление плашки.

### 8. `domcontentloaded` не наступает

hh.ru вечно догружает ресурсы, поэтому `page.goto(..., waitUntil: "domcontentloaded")`
падает по таймауту. Вместо этого ждём `commit`, а нужные элементы — явно.

### 9. Пустые страницы выдачи

На несуществующей странице hh отдаёт счётчик «Найдено N вакансий», но карточек
не рисует. Без проверки на пустую страницу бот молотил бы до `MAX_PAGES`.

### 10. Кнопка письма у каждой карточки своя

На странице несколько откликов, и у каждого своя кнопка «Приложить письмо»
(а на странице анкеты такая кнопка тоже есть). Поэтому карточка ищется по
`vacancyId` (`div[id="<vacancyId>"]` внутри карточки), а не просто «первая кнопка».

### 11. «Отклик уже просмотрен работодателем»

Если работодатель уже открыл отклик, hh не даёт прикрепить к нему письмо —
форма отвечает красным сообщением «Отклик уже просмотрен работодателем»
(класс `magritte-text_style-negative`). Письмо прикрепить нельзя, но сам отклик
уже отправлен. Бот ловит это сообщение, закрывает форму и переходит к следующей
вакансии — такая вакансия считается успешной («отклик без письма»).

Форма письма — модалка, у которой «Закрыть» — обычная текстовая кнопка без
`aria-label` и `data-qa`, а Escape её не закрывает. Поэтому `closeLetterForm()`
ищет кнопку по тексту («Закрыть»/«Отмена») внутри модалки с полем письма, ждёт,
пока поле исчезнет, и, если форма осталась, перезагружает выдачу.

## Таймауты и оптимизация

Все таймауты собраны в объекте `TIMEOUTS` в `bot.constants.ts`:

| Поле | Значение | Зачем |
|---|---|---|
| `appear` | 3 с | модалки, поле письма, кнопки — появляются за 1–2 с |
| `letter` | 6 с | блок «отклик отправлен» — чуть медленнее |
| `nav` | 60 с | навигация |
| `cards` | 20 с | появление карточек |
| `poll` | 100 мс | шаг опроса `waitForEvent` |

Ключевой принцип: **ждать событие, а не таймер**. Вместо `waitForTimeout(N)`
используются `waitFor` по конкретному элементу — бот возвращается в момент
появления элемента, а не выжидает полный таймаут. `waitForEvent()` опрашивает
несколько селекторов сразу, чтобы понять, *что именно* произошло, а не
дожидаться одного конкретного события ценой полного таймаута.

`slowMo` убран (был 50 мс на каждое действие — на сотнях действий давал
ощутимую задержку).

## Обработка ошибок

- Каждая вакансия обёрнута в `try/catch` — сбой на одной не останавливает
  прогон.
- `bestEffort(что, действие)` — для необязательных шагов (закрыть модалку,
  вернуться назад): не валит прогон, но логирует ошибку как
  `⚠️ <что>: <причина>` вместо тишины.
- Предикаты (`isVisible`, `waitVisible`) возвращают `false` вместо исключения —
  это валидный ответ «элемента нет».

## Безопасность

- `sessions/` — зашифрованные cookies (файлы `0600`, папка `0700`), в
  `.gitignore`. Без пароля файл бесполезен, но пароль от hh, слабый к перебору,
  всё равно слабое звено — scrypt лишь делает перебор дорогим.
- Сервер слушает `127.0.0.1` (`HOST`): API принимает пароль от hh, не выставляй
  его в сеть без авторизации и HTTPS.
- Отклик не отзывается: перед запуском проверь число и письмо.
